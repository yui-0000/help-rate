# データベース設計: おらほの助っ人けっぱれーと

## 1. データベース設計の概要

本アプリ（おらほの助っ人けっぱれーと）では、アプリを再起動してもデータが消えないよう、軽量なリレーショナルデータベースである **SQLite** を使用し、PythonのORMである **Peewee** を通じてデータを管理します。

14時間の制作期間（MVP）を考慮し、複雑さを削ぎ落とした最小限の2つのテーブル（UserとTask）で構成しています。

---

## 2. テーブル一覧

| テーブル名 | モデル名 (Peewee) | 役割・概要 |
| --- | --- | --- |
| **users** | `User` | アプリを利用するユーザー（代理投稿者・助っ人）の情報を管理する |
| **tasks** | `Task` | 地域住民から寄せられた「お手伝い案件」の情報を管理する |

---

## 3. 各テーブルの詳細と「なぜそのテーブルが必要なのか」

### ① User（ユーザー）テーブル

* **なぜこのテーブルが必要なのか:**
「簡易ユーザー管理機能」を実現するために必要です。誰がログインしているかを把握し、自分が投稿した案件を識別したり、投稿作成・応募・編集などの権限を制御するためにユーザー情報を保持します。

| 項目名 (カラム名) | データ型 (Peewee) | 制約・属性 | 説明 |
| --- | --- | --- | --- |
| `id` | IntegerField | 主キー (Primary Key), 自動連番 | ユーザーを識別する一意のID |
| `username` | CharField | ユニーク制約 (Unique=True), 必須 | ログインや画面表示に使うユーザー名 |
| `password` | CharField | 必須 | パスワード（※学習・MVP段階では平文または簡易ハッシュ） |
| `role` | CharField | 必須 | 立場（例: 「代理の人」「助っ人」など） |

* **主キー:** `id`
* **ユニーク制約:** `username` （同じ名前のユーザーが重複して登録されるのを防ぐ）
* **インデックス候補:** `username` （ログイン時の検索を高速化するため）

---

### ② Task（お手伝い案件）テーブル

* **なぜこのテーブルが必要なのか:**
アプリのメイン機能である「お手伝い案件の投稿」や「一覧表示・詳細閲覧」を行うためのデータを保存するために必要です。どのユーザーがその案件を投稿したのかを結びつける役割も持ちます。

| 項目名 (カラム名) | Data Type (Peewee) | 制約・属性 | 説明 |
| --- | --- | --- | --- |
| `id` | IntegerField | 主キー (Primary Key), 自動連番 | 案件を識別する一意のID |
| `title` | CharField | 必須 | お手伝いのタイトル（例：「冬前の雪かき用具出し」） |
| `category` | CharField | 必須 | 困りごとの種類（例：「雪かき」「買い物」「農作業」） |
| `content` | TextField | 必須 | 詳しい内容（具体的な作業や状況の説明） |
| `reward` | CharField | 任意 / 必須 | お礼・見返り（例：「りんご1箱」） |
| `user` | ForeignKeyField | 外部キー (`User` と紐付け) | 誰がこの案件を投稿したか（Userのidを参照） |
| `helper_id` | IntegerField | 任意 (Null可) | （※余裕があるとき用）手伝うことが決まった人のユーザーID |

* **主キー:** `id`
* **外部キー:** `user` （`User` テーブルの `id` と結びつき、誰の投稿かを管理する）
* **インデックス候補:** `user` （特定のユーザーが投稿した案件を効率良く引き出すため）

---

## 4. Peeweeで実装する場合の注意点

1. **外部キー（ForeignKeyField）の設定**
* `Task` モデルで `User` を指定する際、`backref='tasks'` を設定しておくと、あるユーザーオブジェクトから `user.tasks` でその人が投稿した全案件を簡単に取得できるようになります。


2. **データベースの初期化と接続**
* アプリ起動時（または最初に一度）に、`db.connect()` と `db.create_tables([User, Task], safe=True)` を実行してテーブルを自動生成する仕組みを `models.py` に記述します。


3. **将来の拡張（Q2で保留した機能について）**
* 複数人での複雑なマッチング管理が必要になった場合は、テーブルを直接改修する代わりに、後から「応募管理（Match）」のような中間テーブルを追加することで、既存の設計を大きく壊さずに機能を拡張できるようにしています。
